# 编码与文档规范（经验固化）

> 这里只放可执行的硬规则。常规来源是 [LESSONS.md](../LESSONS.md) 中同一经验教训出现 **3 次** 后固化的条目；项目所有者直接指定的规则立即固化，不等待计数。不放进度、设计细节或一次性提醒。

## 固化流程

1. 在 `LESSONS.md` 记录现象、教训与做法，并累计"出现次数"。
2. 同一教训第 3 次出现时，在本文件新增一条规则，写明规则、正例/反例与检查方式，并在 `LESSONS.md` 对应条目标注"已固化"。
3. 项目所有者直接指定的规则立即写入本文件并生效。
4. 规则生效后，任务验收与代码评审按本文件检查。

## 规范

### D-001 设计文档描述目标态，不描述实现进度

**规则**

- `docs/architecture.md` 与 `docs/subsystem/*.md` 是项目的**设计目标**：描述系统最终应该是什么样、契约是什么、边界是什么。
- 未实现的功能**保留在设计文档中**，不得因为"代码还没做"而删除设计目标。
- 设计文档不写"已落地 / 已实现 / 尚未实现 / 阶段 N 完成 / 第一版"等进度与变更历史；这些属于 [docs/roadmap.md](roadmap.md) 与 git log。
- 只有当开发过程中发现**实现需要导致设计变更**时，才修改设计文档；修改后仍用描述性口吻写目标态，不写"改了什么"。
- 任务完成后，如果代码事实改变的是**设计契约**（协议、结构、流程、边界），同步改受影响的设计文档；如果只是推进了实现进度，只更新路线图/提交信息，不动设计文档。

**正例**

- 设计文档保留 `session/rename`、固定侧栏、崩溃恢复、自动 resync 等目标能力，即使当前代码还没有实现。
- 实现发现"取消等待必须放在 prompt 被接受之后"才改设计文档中的取消契约，并在提交正文说明契约变化。

**反例**

- 因为代码尚未实现 `session/delete` 就从协议方法表中删掉它。
- 因为当前 UI 是弹窗就把设计文档里的固定侧栏删除。
- 把"P1 已落地"写进架构文档。

**检查方式**

- 改设计文档前先问：是"实现迫使设计变化"，还是"实现还没跟上目标"？后者不改目标。
- 任务提交时区分：设计契约变化（改设计文档）与实现进度变化（改路线图）。
- 设计文档中不应出现进度口吻；路线图中不应出现设计细节的重复维护。
